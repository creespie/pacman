# Ghosts! More ghosts! — Pac-Man

## Description

A complete, playable Pac-Man clone written in Python 3.10+ with
MiniLibX (`mlx`) for the graphics. The player walks a maze, eats every
pacgum before the timer runs out, turns the tables on the ghosts with a
super-pacgum, and works through ten levels — the first one always the
same (fixed seed), the following ones generated at random.

Mazes are not drawn by hand and not generated by us: they come from the
**A-Maze-ing** package written by another group, used as-is.

The project is built around a strict Model–View–Controller split with an
observer in the middle:

* the **model** owns the rules and announces every change as an event;
* the **views** only listen to those events and draw;
* the **controllers** turn key presses into commands and run the frames.

Nothing in the view imports the model, and nothing in the model imports
MiniLibX.

## Instructions

### Install

```sh
make install          # uv sync: creates .venv with every dependency
```

Dependencies that are not on PyPI are vendored in the repository and
installed from there:

* `libs/mazegenerator-2.1.0-py3-none-any.whl` — the assigned A-Maze-ing
  package (never modified, reinstalled as-is during the review);
* `mlx-2.2/ubuntu/` and `mlx-2.2/fedora/` — MiniLibX Python bindings.

### Platform support

MiniLibX 2.2 (CLXV) is **Linux only**: the wheel ships a `libmlx.so`
built for x86-64 Linux and the library links against Vulkan, XCB and
libbsd. It cannot be loaded on macOS — a Mac reports
`slice is not valid mach-o file` — and there is no macOS build to fall
back on. Run the game on the school machines, on any x86-64 Linux box,
or in a Linux VM.

Runtime and build dependencies on Ubuntu:

```sh
sudo apt install libvulkan1 libxcb1 libxcb-keysyms1 libbsd0
# and, to rebuild MiniLibX from mlx-2.2/src:
sudo apt install vulkan-headers libvulkan-dev libxcb1-dev \
                 libxcb-keysyms1-dev libbsd-dev zlib1g-dev
```

Everything that is not the window still works anywhere, macOS included:

```sh
make test      # the whole model, session and config test suite
make lint      # flake8 + mypy
```

On a machine with no GPU (a container, a CI runner), a software Vulkan
driver is enough to run the real game under a virtual display:

```sh
sudo apt install mesa-vulkan-drivers xvfb
VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json \
    xvfb-run -a python3 pac-man.py config.json
```

### Run

```sh
python3 pac-man.py config.json      # exactly one argument: a .json file
make run                            # same thing, inside the venv
make run CONFIG=other.json          # with another configuration
```

### Controls

| key                      | action                                  |
|--------------------------|-----------------------------------------|
| arrow keys / `W` `A` `S` `D` | move Pac-Man, move in the menus      |
| `ENTER` / `SPACE`        | validate                                |
| `ESC`                    | pause during a game, go back elsewhere  |
| `C`                      | toggle cheat mode (see below)           |
| `1` … `5`                | cheats, once cheat mode is on           |

### Cheat mode (for peer review)

Press `C` during a game: the HUD shows `CHEATS`. Then:

| key | cheat                                                  |
|-----|--------------------------------------------------------|
| `1` | invincibility — ghosts no longer take a life           |
| `2` | freeze ghosts                                          |
| `3` | speed boost (x1.8)                                     |
| `4` | one extra life                                         |
| `5` | skip the level (counts as cleared)                     |

Pressing `C` again turns cheat mode off and clears every flag. Cheat
keys do nothing while cheat mode is off, so they cannot be triggered by
mistake. With `5` the whole ten-level progression, the victory screen
and the highscore entry can be reviewed in a few seconds.

## Configuration

The file passed on the command line is JSON with comments: everything
after a `#` or a `//` that is outside a JSON string is ignored, on any
line. The program takes exactly one argument and it must end in `.json`.

| key                        | default            | meaning                                                            |
|----------------------------|--------------------|--------------------------------------------------------------------|
| `highscore_filename`       | `highscores.json`  | where the top ten are stored                                        |
| `levels`                   | `10`               | levels to clear to win                                              |
| `width`, `height`          | `21`, `21`         | maze size in cells (the generator gets half of it)                  |
| `lives`                    | `3`                | starting lives                                                      |
| `pacgum`                   | `999`              | maximum pacgums per level; above the number of corridors, they all get one |
| `points_per_pacgum`        | `10`               | score for a pacgum                                                  |
| `points_per_super_pacgum`  | `50`               | score for a super-pacgum                                            |
| `points_per_ghost`         | `200`              | score for an edible ghost                                           |
| `seed`                     | `42`               | seed of the first level; later levels are random                    |
| `level_max_time`           | `150`              | seconds allowed per level                                           |

**Why 150 seconds.** A 21x21 maze has about 224 corridors and, with
`pacgum: 999`, a pacgum in every one of them. The shortest route that
collects them all is roughly 310 cells, i.e. ~62 s at Pac-Man's speed
with no mistake and no ghost to dodge — so a 90 s limit made a level
unclearable in practice. Lower `pacgum` (e.g. `80`) or shrink the maze
if a shorter level is wanted instead.

**Faulty configuration.** A missing key, a wrong type or an out-of-range
value never stops the game: the value is clamped to a safe default, a
line is printed on `stderr` (`config: 'lives' must be at least 1, got
-3, clamped`), and the game starts. Unknown keys are reported and
ignored. Only a file that cannot be read at all, or that is not valid
JSON, is fatal — and even then the player gets one clear line, never a
traceback.

## Highscore

Implemented in `src/pacman/model/highscore.py` as a small JSON file (a
list of `{"name": ..., "points": ...}` objects), loaded when the game
starts and written every time a score is added.

Why this way: a highscore table is the one place where a crash is the
least acceptable and the least useful. JSON keeps it inspectable and
editable by hand during the review, and the file is small enough that
rewriting it whole on each entry costs nothing. The table therefore
never raises:

* a missing file means an empty table (first run);
* unreadable or invalid JSON is reported and treated as empty;
* entries with a wrong shape or a negative score are dropped on load;
* names are sanitized (alphanumerics and spaces, ten characters max,
  `PLAYER` if nothing is left), both when typed and when read back;
* only the ten best are kept, sorted by score;
* a failed write is reported, and the game carries on.

The table is displayed in the main menu (best score) and on its own
screen, and the player is asked for a name after both a game over and a
victory.

## Maze Generation

We do not generate mazes. `src/pacman/model/maze.py` adapts the assigned
A-Maze-ing package to what the game needs — the loader adapts to their
interface, never the opposite:

1. `MazeGenerator(size=(width // 2, height // 2), perfect=False,
   seed=...)` is instantiated. `perfect=False` is required by the
   subject: it produces loops, so Pac-Man corridors instead of a
   single-solution maze.
2. `generator.maze` gives a grid of bitmasks, one per generated cell,
   where each bit is a wall (`NORTH`, `EAST`, `SOUTH`, `WEST`). A cell
   with all four bits set is one of the package's decorative "42" cells
   and is left solid.
3. Each generated cell becomes a 2×2 block plus a one-cell border in our
   own spatial grid (`0` floor, `1` wall), which is why the generator
   receives half of the configured size: `21` cells of game grid come
   from `10` generator cells.
4. Anything the package raises is caught and turned into a clean
   message: a failing generator sends the player back to the main menu
   instead of killing the process.

The first level uses `seed` from the configuration (42 by default), so
it is always the same; every level after that uses a random seed.

## Implementation

**Coordinates.** One convention, written down once in
`protocol/events.py` and followed everywhere: a position is a point in
cell units, the cell containing it is `(int(x), int(y))`, and the centre
of a cell is `(col + 0.5, row + 0.5)`. The model sends centres, the view
multiplies by the cell size in pixels and adds nothing. Fixing the
half-cell mismatch between the two sides was the point of the last pass
on the code.

**Real-time rendering through events.** The model never calls the view.
It emits `MazeGenerated`, `FoodSpawned`, `FoodCollected`, `PacmanMoved`,
`GhostMoved`, `GhostStateChanged`, `ScoreChanged`, `LivesChanged`,
`LevelStarted`, `TimeChanged`, `PacmanCaught`, `CheatsChanged`,
`LevelCompleted`, `GameOver` and `GameWon`; the session adds the screen
events (`ScreenChanged`, `MenuChanged`, `HighscoresChanged`,
`NameEntryChanged`). A view stores what it receives and draws only in
`render()`, which the application calls once per frame. A whole level
can therefore be described to a view that just connected, simply by
replaying the events (`Game.start()` does exactly that).

**Two drawing layers.** The maze and the uneaten pacgums are painted
once into a background image; a frame is one `memcpy` of that image plus
the five moving entities. Eating a pacgum repaints a single cell of the
background instead of the whole maze.

**The drawing budget, and why menus are not repainted.** MiniLibX queues
its blits and flushes them to the screen as soon as 64 are pending
(`VK_NB_DRAW`). An image counts as one blit and *every character* of
`mlx_string_put` counts as one too, so a frame carrying more than ~63
characters is presented in two pieces and the text visibly flickers.
Two things come out of that:

* `Canvas.present()` ends with `mlx_do_sync()`, so one call to `present`
  is exactly one frame on screen instead of whatever MiniLibX decides to
  cut in the middle;
* the view only repaints a screen that can have changed. A running game
  moves on every frame and is always redrawn — its HUD costs 47 blits of
  the 64 available, which `tests/test_view.py` checks — while the menus,
  the pause screen and the end screens are static and are redrawn only
  when an event changed them, or when the window is uncovered (the
  expose hook calls `MlxView.invalidate`).

**Movement.** Entities move in cells per second and are only allowed to
turn on a cell centre. "Being on a centre" is not a fixed epsilon but
half of the distance covered during the current frame, so an entity is
never sampled past an intersection it should have taken, whatever the
frame rate. On each turn the position is snapped to the exact centre,
which kills the drift that would otherwise accumulate in floating point.
Requested turns are remembered (`next_direction`), so a turn asked for
slightly too early is still taken.

That last point needs two numbers, and they answer different questions.
`_is_centred` answers "did this entity go through a centre during this
frame?", and its tolerance has to be half a frame's step or a slow frame
skips the intersection — it is a detection threshold and it rightly
follows the frame rate. `_can_turn` answers "is Pac-Man close enough to
a centre to turn?", which is geometry, not timing: `TURN_WINDOW = 0.2`
cells, fixed. Reusing the first for the second made the controls sluggish
— at 60 fps the window was 0.042 cells, so most of the 200 ms between two
centres simply threw the input away, and it got *worse* on a faster
machine. Ghosts keep `_is_centred`; only Pac-Man uses the wider window.
A request also expires after `TURN_REQUEST_TIMEOUT`, so a turn pressed
against a wall no longer fires by itself at some unrelated intersection
seconds later.

**Ghosts.** Each of the four picks, at every intersection, the direction
that minimises the squared distance to Pac-Man — and maximises it while
frightened. They never reverse unless it is the only way out. Eaten
ghosts are invisible and harmless until they respawn in their corner
after 7 seconds.

**Frames.** `App.tick()` advances the game by the time really elapsed
since the previous frame, capped at 100 ms so that a stall cannot teleport
anything through a wall. It is plugged into the MLX loop hook in the
real game, and called by a plain loop in the tests — the model does not
know the difference.

**Errors.** No code path is allowed to show a traceback: the
configuration is clamped, the generator is wrapped, the highscore file
is defensive, and `__main__` catches whatever is left.

## General Software Architecture

```
pac-man.py                 launcher required by the subject
src/pacman/
├── __main__.py            CLI parsing, wiring, window creation
├── config.py              tolerant JSON-with-comments loader
├── protocol/              the shared vocabulary (no logic at all)
│   ├── enums.py           Direction, FoodType, GhostState, Screen, Cheat
│   ├── events.py          model -> views messages
│   └── commands.py        controllers -> model/session messages
├── utils/observer.py      generic Observable / Observer
├── model/                 the rules; imports no view, no MLX
│   ├── game.py            state machine of a run, emits every event
│   ├── maze.py            adapter over the A-Maze-ing package
│   ├── collision.py       walls and entity/entity collisions
│   ├── food.py            pacgums and super-pacgums
│   ├── highscore.py       persistent top ten
│   └── entities/          Entity -> Pacman, Blinky
├── view/                  drawing only; imports no model
│   ├── base.py            View: dispatches events to handlers
│   ├── canvas.py          the only file that imports mlx
│   ├── mlx_view.py        every screen, drawn from stored event state
│   └── console.py         text view, used with PACMAN_DEBUG=1
└── controller/
    ├── app.py             frame loop: input -> model -> render
    ├── session.py         screen flow (menu, game, pause, name entry)
    ├── input_handler.py   InputHandler interface
    └── keyboard.py        keycodes -> commands, per active screen
tests/                     pytest suite (config, highscore, model, session)
stubs/                     type stubs for the two vendored packages
```

Data flows in one direction: key press → `KeyboardInput` → `Command` →
`Session` (or `Game`) → `Event` → `View` → pixels. The session is also
an observer of the model, which lets it forward every model event to the
views and react to `GameOver` / `GameWon` without the model knowing that
screens exist.

Swapping MiniLibX for another library means rewriting `canvas.py` and
nothing else. Adding a network client means adding a view and an input
handler; the protocol is plain data on purpose.

## Packaging

`pac-man.spec` at the root is the PyInstaller specification.

```sh
make package        # -> dist/pac-man/
cd dist/pac-man && ./pac-man config.json
```

`EXE(contents_directory=".")` in the spec keeps the shipped
`config.json` and `README.md` next to the executable instead of hiding
them in PyInstaller 6's `_internal/` folder, so the command above works
and a player can edit the configuration of the packaged game.

The folder in `dist/` is the one uploaded to itch.io as a free, unlisted
Linux build. It must be built on the target distribution, because the
MiniLibX shared object links against the system X11 libraries.
